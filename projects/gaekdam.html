Gaekdam – B2B 호텔 CRM

예약·투숙·운영·자동 메시징을 통합 관리하는 SaaS 기반 호텔 CRM 시스템입니다.

  • JAVA
  • Python
  • Spring
  • MyBatis
  • Vue
  • MariaDB
  • Redis
  • AWS

개발 기간

2026.01.01 ~ 2026.02.10

팀 구성

4인 · 참여 프로젝트

담당 업무

예약통합관리, 여정 메세징, AWS 배포

배경 및 필요성

  • 기존 CRM 솔루션의 한계: 호텔 산업의 고객 여정 특성을 반영하지 못하여 재방문 유도, VIP 관리, 맞춤형 서비스 제공에 한계가 있음
  • 고객 응대의 중요성: 브랜드 신뢰도에 직결되는 핵심 영역이나, 직원 개인 역량에 의존하는 구조로 품질 편차 발생
  • 보안 체계 강화 필요: 고객의 개인정보 및 민감정보를 다량 처리하며, 법적 규제 준수 및 신뢰성 있는 보안 체계 구축이 필수
  • 연간 운영 목표 관련 성과 지표 파악 기능 부족: 성과 지표를 명확히 파악·관리할 수 있는 기능이 부족하여 효과적인 성과 추적이 어려운 상황

담당 기능 개발

  • 통합 예약관리
  • 투데이 객실현황 및 부대시설 이용현황
  • 투숙여정 타임라인
  • 여정단계별 자동 메세징 처리 (템플릿 커스텀)
  • AWS 서비스 배포

Review

통합예약관리를 위해서 많은 참조가 필요했습니다. 그에 따라서 CQRS 방식으로 복잡한 조회 쿼리를 MyBatis를 통해서 구현하는 방식을 이번에 제대로 써본 거 같아 좋은 경험이 되었습니다. 또 나아가 AWS를 통한 배포를 직접 해보면서 AWS에 있는 많은 기능들을 사용해 볼 수 있었어 값진 시간이 되었습니다.

자료 링크

화면설계서 (Figma) DB 설계 (ERD Cloud) GitHub 레포 PPT 발표자료

개발 중 이슈

5명의 팀원으로 시작하였으나 중간에 1명의 팀원이 이탈하는 상황이 발생했다. 여정그룹과 설문, 리워드, 메세징 부분을 맡아서 진행하기로 한 팀원이 마감 2주 남은 상태에서 아무것도 해놓지 않은 상태로 말도 없이 이탈해버렸습니다. 팀원 모두 각자 할 일이 있고 그렇다고 저 기능들을 빼놓고 갈 수는 없어서 막막했습니다. 얘기하던 중 원래의 기능에서 설문·리워드 제외, 유저가 커스텀하게 지정하는 기능을 삭제, 메세징 채널·여정단계·방문유형을 고정하여 기능을 축소하는 게 어떻냐고 제안을 했고, 팀원들의 긍정적인 의견을 받고 진행하여서 마감기간 전에 완수할 수 있었습니다.
프로젝트를 진행하면서 깃허브 이슈관리를 통해 기능별로 조금씩 브랜치를 나눠서 각자 작업하고 해당 브랜치를 develop 브랜치에 머지하는 방식을 선택해 진행하였습니다. 하지만 이런 식으로 기능별로 작게 나누어 작업하여도 충돌문제는 피할 수 없었습니다. 1. 한 브랜치에서 장시간 작업하는 경우 2. 새로운 반영 사항들을 최신으로 받지 않고 작업하는 경우 각자의 브랜치에 계속 예전 코드들이 존재하는 경우가 있어서 몇 번씩 합치는 과정에서 충돌문제를 겪었습니다. 그래서 저희는 매일 아침 10시에 일일 회의를 진행하며 각자의 진행상황, 문제상황, 진행예정상황을 공유하며 한 번씩 브랜치를 최신상태로 합치는 방법을 진행해보았습니다. 이 방법이 처음엔 귀찮기도 하고 번거롭기도 했지만 프로젝트가 진행될수록 점점 전에 있던 기능·코드 충돌들이 사라지면서 작업하는 시간을 좀 더 효율적으로 사용할 수 있게 되었습니다. 프로젝트를 진행하면서 이러한 형상관리 작업방식에 대한 체계적인 소통방식의 중요성을 알 수 있는 좋은 경험이었습니다.
B2B 호텔 CRM 프로젝트를 진행하면서 50만 건이 넘어가는 대량 데이터를 다루어 보았습니다. 그에 따라서 몇 가지 문제가 생겼는데 1. 더미데이터 Insert 시간 2. 통합데이터 조회 응답시간 [1] 대량의 더미데이터를 Java 코드를 작성하여 JPA 방식으로 데이터 생성을 하였습니다. 여기서 문제가 발생했는데 몇십만 건을 JPA 방식으로 일일이 집어넣다 보니 영속성 캐시가 계속 쌓이고, 하나하나 save를 발생시키면서 데이터 생성시간이 기하급수적으로 늘어나며 메모리 초과가 발생했습니다. 첫 번째 해결 방안으로 엔티티매니저를 통해 insert 반복문마다 캐시를 초기화하고, 스프링 BATCH 기능을 통해 save를 모아서 처리했습니다. 이 방식을 통해서 확실히 생성시간을 절반 넘게 줄였지만 그래도 오래 걸렸습니다. 두 번째 해결방안으로 기존 JPA 생성방식에서 JDBC 방식을 통해 영속성 관리를 아예 해제해버리는 방법을 시도했습니다. 이 방법을 통해 직접 쿼리문을 통해 집어넣으니 90% 이상 생성시간이 줄어들어 최종적으로 이 방법을 선택하였습니다. [2] 우리 CRM의 특성상 많은 정보를 엮어서 통합적으로 보여줘야 될 경우가 많았습니다. 그래서 많은 엔티티들이 조인되며 조회가 되었는데, 데이터가 적을 때는 문제가 없었지만 데이터가 많아지면서 조회속도가 현저히 떨어지며 적게는 2초, 많게는 5초 넘게 걸리는 경우도 발생했습니다. 해결방안으로 불필요한 조인 삭제와 DB 인덱스 설정을 통해 풀스캔을 방지하고, 페이징을 통해 개수를 제한했습니다. 이 방식을 통해 통합 조회시간을 95% 이상 줄여나갔습니다.
