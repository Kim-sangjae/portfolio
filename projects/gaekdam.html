Gaekdam – B2B 호텔 CRM

예약·투숙·운영·자동 메시징을 통합 관리하는 SaaS 기반 호텔 CRM 시스템입니다.

  • JAVA
  • Python
  • Spring
  • MyBatis
  • Vue
  • MariaDB
  • Redis
  • AWS

개발 기간

2026.01.01 ~ 2026.02.10

팀 구성

4인 · 참여 프로젝트

담당 업무

예약통합관리, 여정 메세징, AWS 배포

배경 및 필요성

  • 기존 CRM 솔루션의 한계: 호텔 산업의 고객 여정 특성을 반영하지 못하여 재방문 유도, VIP 관리, 맞춤형 서비스 제공에 한계가 있음
  • 고객 응대의 중요성: 브랜드 신뢰도에 직결되는 핵심 영역이나, 직원 개인 역량에 의존하는 구조로 품질 편차 발생
  • 보안 체계 강화 필요: 고객의 개인정보 및 민감정보를 다량 처리하며, 법적 규제 준수 및 신뢰성 있는 보안 체계 구축이 필수
  • 연간 운영 목표 관련 성과 지표 파악 기능 부족: 성과 지표를 명확히 파악·관리할 수 있는 기능이 부족하여 효과적인 성과 추적이 어려운 상황

담당 기능 개발

  • 통합 예약관리
  • 투데이 객실현황 및 부대시설 이용현황
  • 투숙여정 타임라인
  • 여정단계별 자동 메세징 처리 (템플릿 커스텀)
  • AWS 서비스 배포

Review

통합 예약 관리 화면은 여러 테이블의 정보를 한 번에 보여줘야 해서 조회 로직이 꽤 복잡했습니다. 데이터를 "저장하는 방식"과 "조회해서 보여주는 방식"을 분리해서 설계하는 CQRS 패턴을 이번에 제대로 적용해봤고, 복잡한 조회는 MyBatis로 직접 SQL을 작성해 구현했습니다. 또 AWS를 통한 배포를 직접 해보면서 AWS의 여러 기능을 실제로 사용해볼 수 있었던 것도 값진 경험이었습니다.

자료 링크

화면설계서 (Figma) DB 설계 (ERD Cloud) GitHub 레포 PPT 발표자료

개발 중 이슈

5명의 팀원으로 시작하였으나 중간에 1명의 팀원이 이탈하는 상황이 발생했다. 여정그룹과 설문, 리워드, 메세징 부분을 맡아서 진행하기로 한 팀원이 마감 2주 남은 상태에서 아무것도 해놓지 않은 상태로 말도 없이 이탈해버렸습니다. 팀원 모두 각자 할 일이 있고 그렇다고 저 기능들을 빼놓고 갈 수는 없어서 막막했습니다. 얘기하던 중 원래의 기능에서 설문·리워드 제외, 유저가 커스텀하게 지정하는 기능을 삭제, 메세징 채널·여정단계·방문유형을 고정하여 기능을 축소하는 게 어떻냐고 제안을 했고, 팀원들의 긍정적인 의견을 받고 진행하여서 마감기간 전에 완수할 수 있었습니다.
깃허브 이슈 관리를 통해 기능별로 각자의 작업 공간(브랜치)을 나누고, 완료되면 develop이라는 공통 작업 공간에 합치는(머지) 방식으로 진행했습니다. 하지만 이렇게 기능별로 작게 나누어 작업해도 코드가 서로 충돌하는 문제는 피할 수 없었습니다. 1. 한 작업 공간에서 너무 오래 작업하는 경우 2. 다른 사람이 반영한 최신 코드를 받지 않고 예전 코드 위에서 계속 작업하는 경우 이런 경우가 쌓이면서 나중에 합칠 때마다 충돌 문제를 자주 겪었습니다. 그래서 매일 아침 10시에 일일 회의를 열어 각자의 진행 상황과 문제 상황을 공유하고, 그때마다 최신 코드를 받아 자신의 작업 공간을 최신 상태로 맞추는 방법을 진행했습니다. 처음엔 귀찮고 번거로웠지만, 프로젝트가 진행될수록 코드 충돌이 눈에 띄게 줄어들면서 작업 시간을 훨씬 효율적으로 쓸 수 있게 되었습니다. 이 경험을 통해 협업 시 코드 관리 방식과 팀 간 소통 체계가 왜 중요한지 확실히 알 수 있었습니다.
B2B 호텔 CRM 프로젝트를 진행하면서 50만 건이 넘는 대량의 테스트 데이터를 다루게 됐습니다. 그러면서 두 가지 문제가 생겼습니다. 1. 테스트용 가짜 데이터를 채워 넣는 데 걸리는 시간 2. 여러 정보를 한 화면에 모아 보여주는 통합 조회 화면의 응답 속도 [1] 처음에는 자바로 코드를 작성해 일반적인 데이터베이스 처리 방식(JPA)으로 데이터를 한 건씩 저장했습니다. 그런데 데이터가 몇십만 건 쌓이면서 저장 속도가 갈수록 느려지고, 결국 메모리가 부족해지는 문제까지 발생했습니다. 먼저 저장 과정에서 쌓이는 임시 캐시를 주기적으로 비우고, 데이터를 한 건씩이 아니라 여러 건씩 묶어서 저장하는 방식(스프링 배치)으로 바꿔 시간을 절반 넘게 줄였습니다. 그래도 여전히 오래 걸려서, 이후에는 좀 더 직접적인 방식(JDBC)으로 SQL을 실행해 데이터를 넣도록 바꿨더니 저장 시간이 90% 이상 줄어들어 최종적으로 이 방법을 선택했습니다. [2] CRM 특성상 여러 테이블의 정보를 하나로 묶어서 보여줘야 하는 화면이 많았습니다. 데이터가 적을 때는 문제가 없었지만, 데이터가 많아지면서 조회 속도가 크게 떨어져 화면을 불러오는 데 2~5초 넘게 걸리는 경우도 있었습니다. 불필요하게 여러 테이블을 한꺼번에 엮어서 조회하던 부분을 줄이고, 검색 속도를 높여주는 데이터베이스 색인(인덱스)을 추가했습니다. 또 한 번에 불러오는 데이터 양을 제한하는 방식(페이징)을 적용해, 통합 조회 시간을 95% 이상 줄일 수 있었습니다.
