개발 중 이슈

기존에는 안 쓰던 네이버 소셜 로그인을 같이 써보았다. 하지만 소셜로그인 할 때는 필요한 API 값이 정해져있어, 일반유저와 소셜로그인을 같이 구현할 때 가져오는 API에 따라 필요값이 달라진다. 우리가 기존에 만들어놨던 방식이랑 다른 것이다. 같은 User 객체를 가지고 설계를 했기 때문에 해결방법이 필요했다. - 일반유저 → 로그인아이디를 email로 사용, pw 값 필수 - 소셜유저(네이버) → pw 초기값이 들어가면 안 되고, loginId 값이 따로 들어가야 함 기존에 SpringBoot의 생성자를 통해서 User를 생성하면 소셜 로그인과 계속 충돌이 남. 이를 해결하기 위해 생성자가 아닌 메서드 형태로 일반, 소셜 로그인을 따로 만들어서 값을 초기화 시킨다. 
// Entity에 생성자가 아닌 static 메서드 형태로 정의

// 일반 회원가입용
public static User createNormalUser(String email, String password, String nickname) {
    return User.builder()
            .userEmail(email)
            .userPassword(password)
            .userNickname(nickname)
            .userRole(Role.USER)
            .userStatus(Status.Y)
            .build();
}

// 소셜 로그인용
public static User createSocialUser(String loginId, String email, String nickname) {
    return User.builder()
            .userLoginId(loginId)
            .userEmail(email)
            .userNickname(nickname)
            .userPassword("")  // 소셜 로그인은 비밀번호 없음
            .userRole(Role.USER)
            .userStatus(Status.Y)
            .build();
}

초기에는 WebSocket 채팅 메시지 처리 시점에도 HTTP 요청처럼 JWT 토큰을 계속 검사하려고 했다. 하지만 STOMP 기반 WebSocket 메시지는 일반적인 HTTP 요청과 달리 매 요청마다 Authorization 헤더를 동일하게 처리하지 않았고, @MessageMapping 단계에서 사용자 인증 정보를 안정적으로 가져오기 어려웠다. WebSocket은 최초 CONNECT 이후 연결을 유지하는 구조이기 때문에, REST API처럼 매 메시지마다 토큰을 재검증하는 방식이 맞지 않았다. 즉, 메시지 처리 단계에서 헤더 기반 인증을 기대한 것이 문제였다. 그래서 이를 해결하기 위해 클라이언트가 STOMP CONNECT 시점에만 JWT를 전송하고, 서버에서는 HandshakeInterceptor에서 처음 토큰을 검증한 뒤 사용자 정보를 WebSocket 세션 또는 Principal에 저장하도록 구조를 변경했다. 이후 @MessageMapping에서는 토큰을 다시 받지 않고, 세션에 저장된 사용자 정보를 꺼내 메시지를 처리하도록 수정했다.
