Review

일반적인 HTTP 응답 방식이 아닌 실시간 통신을 위한 웹소켓을 도입하여 많이 헤매던 게 있었지만 좋은 경험이 되었던 프로젝트였습니다. 특히 채팅의 기록을 읽고 저장하기 위해 기존에 사용하던 테이블형식의 RDBMS를 떠나 MongoDB를 사용해보았던 게 기억에 남습니다. MSA 방식을 간소하게라도 사용하기 위해 웹소켓 채팅쪽 서비스를 분리하여 통신을 해본 것도 좋은 경험이었습니다.

개발 중 이슈

기존에는 없던 네이버 소셜 로그인을 새로 추가하게 됐습니다. 그런데 일반 회원가입과 소셜 로그인은 저장해야 하는 값이 서로 달랐습니다. - 일반 회원: 이메일을 아이디로 사용, 비밀번호 필수 - 소셜 회원(네이버): 비밀번호 없이 네이버에서 받은 고유 아이디로 가입 두 방식 모두 같은 회원(User) 데이터 구조를 함께 써야 했기 때문에, 가입 방식에 따라 필요한 값만 다르게 채워 넣는 방법이 필요했습니다. 그래서 회원을 만드는 방법을 하나로 통일하지 않고, "일반 회원 만들기"와 "소셜 회원 만들기"를 각각 별도의 함수로 나누어 필요한 값만 채우도록 구현했습니다. 실제 구현은 아래와 같습니다. 
// 하나의 생성자 대신, 목적이 분명한 함수 두 개로 나눠 정의

// 일반 회원가입용
public static User createNormalUser(String email, String password, String nickname) {
    return User.builder()
            .userEmail(email)
            .userPassword(password)
            .userNickname(nickname)
            .userRole(Role.USER)
            .userStatus(Status.Y)
            .build();
}

// 소셜 로그인용
public static User createSocialUser(String loginId, String email, String nickname) {
    return User.builder()
            .userLoginId(loginId)
            .userEmail(email)
            .userNickname(nickname)
            .userPassword("")  // 소셜 로그인은 비밀번호 없음
            .userRole(Role.USER)
            .userStatus(Status.Y)
            .build();
}

처음에는 실시간 채팅(웹소켓) 메시지를 처리할 때도, 일반 API 요청처럼 메시지마다 로그인 토큰(JWT)을 매번 검사하려고 했습니다. 하지만 웹소켓은 한 번 연결하면 이후로는 계속 이어지는 방식이라, 매 메시지마다 토큰을 새로 확인하는 방식 자체가 맞지 않았습니다. 그래서 방식을 바꿔서, 클라이언트가 채팅 서버에 처음 연결하는 시점에만 로그인 토큰을 보내 서버가 한 번 검증하고, 확인된 사용자 정보를 연결이 유지되는 동안 계속 저장해두도록 했습니다. 이후에는 메시지를 주고받을 때마다 토큰을 다시 확인하지 않고, 처음에 저장해둔 사용자 정보를 그대로 사용하도록 구조를 바꿨습니다.
