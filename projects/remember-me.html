remember-me – AI 개인비서 앱

매일 저녁 AI와 문답으로 하루를 기록하고, 다음 날 아침 그 기록·일정·기억을 바탕으로 브리핑을 받는 개인비서 서비스입니다. Android/iOS 정식 출시를 목표로 개발 중이며, 기획·설계·검증을 직접 담당하고 구현은 Claude Code에 위임하는 방식으로 진행하고 있습니다.

  • Flutter
  • Spring Boot 3
  • Java 21
  • Spring Security (JWT)
  • PostgreSQL
  • pgvector
  • OpenAI API
  • Cloudflare R2
  • Docker
  • GitHub Actions

개발 기간

2026.07 ~ 진행중

팀 구성

1인 · 개인 프로젝트
Claude Code에 구현 위임

담당 업무

요구사항 정의, 아키텍처/도메인 규칙 설계, 기술 결정(ADR) 및 검증 — 코드 구현은 Claude Code 담당

주요 기능

기록 & 기억

  • 텍스트 기록 작성(사진 첨부 포함), soft delete로 삭제해도 복구 여지는 남기되 재노출은 차단
  • AI(OpenAI)가 기록에서 사람·날짜·장소 등 유형별 기억을 자동 추출 — 사용자가 확인·승인해야 확정 기억으로 저장
  • 마이페이지에서 기억을 유형별로 필터링해 확인

AI 문답 & 브리핑

  • 저녁 회고: AI와 최대 8턴 문답을 주고받으며 하루를 기록 (질문 건너뛰기 가능)
  • 아침 브리핑: 오늘 일정·마감 임박 할 일·확정 기억을 근거로 AI가 추천 카드 생성
  • Ask: 저장된 기록·기억에 자연어로 질문하면 근거 목록과 함께 답변 (키워드 검색 → 답변 생성 2단계)

일정 & 그룹

  • 할 일·일정 관리, 월간 캘린더에서 기록·일정·할 일을 한눈에 확인
  • 초대코드 기반 가족/친구 그룹 — 그룹 전용 기록·기억·캘린더를 멤버끼리 공유
  • JWT 인증(refresh 토큰 회전·재사용 감지), 시간대·알림 시간 설정, 계정 삭제(연관 데이터 전체 정리)

설계 포인트

  • 모든 날짜/시간 계산은 사용자 시간대 기준 전용 유틸로만 처리 — 서버는 UTC로 돌기 때문에 직접 계산하면 "오늘/내일"이 사용자 기준과 어긋나는 버그로 이어짐
  • AI가 추출한 정보(이름·날짜 등)는 사용자가 확인하기 전엔 확정 기억으로 승격하지 않음 — AI의 오탐지가 그대로 기록에 남는 것을 방지
  • AI 분석 성공 여부와 무관하게 사용자가 입력한 원본 텍스트/사진은 항상 먼저 저장 — AI 처리가 실패해도 원본 유실은 없도록 분리
  • 리소스 조회는 예외 없이 findByIdAndUserId 패턴만 사용 — ID만으로 조회하면 다른 사용자 데이터가 실수로 반환될 수 있음
  • 기술 선택 배경과 트레이드오프는 ADR로 기록하고, 확정이 아닌 재검토 조건까지 함께 남김

Review

코드를 직접 타이핑하기보다, 요구사항을 명확히 정의하고 설계·검증에 집중하는 방식으로 진행하고 있는 프로젝트입니다. CLAUDE.md에 도메인 규칙을, ADR에 기술 결정 배경을 문서화해 Claude Code가 일관된 방향으로 구현하도록 이끌고, phase 단위로 작업을 쪼개 하나씩 완료 상태를 확인하며 진행합니다. cs-quiz에서 쓰던 협업 방식을 재사용 가능한 템플릿으로 뽑아 이 프로젝트에 가져왔는데, 그대로 믿고 쓰기보다 실제로 의도대로 동작하는지 Claude Code에게 공식 문서와 대조 검증을 지시했습니다. 그 결과 안전장치(hooks)가 겉보기엔 설정돼 있지만 실제로는 아무것도 막지 못하고 있었다는 것을 포함해 여러 문제를 찾아 고칠 수 있었습니다. AI에게 무엇을, 어디까지 맡길지 설계하고 그 결과를 검증하는 것도 개발 역량의 일부라는 걸 체감하고 있습니다.

개발 중 이슈

cs-quiz에서 쓰던 "Claude Code와 협업하는 방식"(규칙 문서, 위험 명령어 차단 hooks, 자동 품질검사 hooks, 단계별 자율 실행 스크립트)을 재사용 템플릿으로 뽑아 이 프로젝트에 가져왔습니다. 설정 파일은 그럴듯해 보였지만 실제로 의도대로 동작하는지 확신이 없어서, Claude Code에게 Claude Code 공식 문서와 실제 동작을 하나하나 대조 검증하도록 지시했습니다. 그 결과 위험 명령어 차단 hook이 애초에 입력 데이터를 받지 못하고 있었던 것, 감지해도 종료 코드가 잘못돼 실제로는 막지 못했던 것, Windows 환경에서 훅 실행 명령 자체가 깨진 python 별칭 때문에 호출조차 안 됐을 수 있었던 것 등 여러 문제를 찾아냈습니다. 문제와 원인, 수정 내용을 전부 문서로 남기도록 해서 재발을 방지했고, 이후 새 프로젝트를 시작할 때도 검증되지 않은 설정을 그대로 믿지 않는 습관이 생겼습니다.
기존 템플릿의 품질검사 스크립트는 프로젝트 루트에 마커 파일(package.json 등) 하나만 있는 구조를 가정하고 있었는데, remember-me는 루트가 아니라 server/(Gradle)와 client/(Flutter) 하위에 각각 마커 파일이 있는 모노레포 구조라 기존 방식으로는 감지가 안 됐습니다. 루트 마커 감지 로직은 그대로 두고, server/·client/ 하위 디렉터리를 별도로 감지해 매치되는 스택을 전부 실행하도록 확장했습니다. 이후로는 코드를 수정하고 나면 서버(Gradle 테스트)와 클라이언트(Flutter analyze·test) 검증이 자동으로 함께 돌아가도록 만들었습니다.
